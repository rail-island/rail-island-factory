# Procedural model factory

Status: agreed
Date: 2026-10-13
Area: whole repository (new): model generator + build, Solid catalog site, Cloudflare deploy pipeline

## Context of the change

`rail-island-factory` is empty: a one-line `README.md` and a `.gitignore`.

In `rail-island-webapp`, branch `ccr-5f803b9b-ohwby3` (commit `6d49d6f`, "ten
procedurally generated skyscrapers") adds code-generated building models:

- `scripts/models/procedural/meshBuilder.ts` - a small, three.js-free mesh builder
  (rings lofted between heights, flat-shaded triangle soup, one primitive per
  material, plain `baseColorFactor` materials) that writes a self-contained GLB.
- `scripts/models/procedural/skyscrapers.ts` - ten `sky-*` designs plus a palette.
- `scripts/models/procedural/generate.ts` - writes `<id>.glb` and a 512 px
  `<id>.png` thumbnail per design into a gitignored folder, deterministically
  (byte-identical output for an unchanged design, thumbnail re-rendered only on
  change, files of removed designs deleted).
- The thumbnail comes from the webapp's offline software rasterizer
  (`scripts/models/renderGlbThumb.ts` over `glbTriangles.ts`, `pngjs`).
- `test/proceduralBuildings.test.ts` checks winding, triangle budget (< 4,000),
  base at y = 0, height > 2x width, and catalog consistency.
- `docs/gameplay/procedural-skyscrapers.md` documents it.

The webapp's `/creator` page (`src/creator/`, Solid, ~4,400 lines) lists every
shipped GLB from a build-generated `models-catalog.json`: a table and a card view,
sort on any column, filters and search, and a click-to-open interactive three.js
preview of the real `.glb`. It also carries sign-in, uploads, woods and packages,
which need the webapp's Worker.

The webapp deploys through GitHub Actions (`pnpm`, Node 22, `wrangler deploy`,
secrets `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`, a custom domain on
`railisland.com` provisioned on deploy). Its hosted embedded build is an
assets-only Worker with no bindings - the closest precedent for a static site.

The goal is to move model generation out of the game into its own repository with
its own viewer, so models can be developed and looked at without the game.

## User request

In the rail-island-webapp repo, branch `ccr-5f803b9b-ohwby3`, there are new GLB
skyscraper models generated by code. Migrate this code into the
rail-island-factory repo. Running the build in the factory repo ("npm build")
builds the GLBs. Also create a frontend running on `factory.railisland.com`,
deployed to Cloudflare, on SolidJS, which shows the models in this repo in the
same way the creator in the webapp repo does its job. Also create a pipeline
deploying to Cloudflare in the same way the webapp does. Change only the factory
repo.

## Decisions

### What is the factory's relationship to the webapp going forward?
| Option | What it means |
|---|---|
| Source for later import | Factory owns generated models; its build emits a vlakosimdb-style export (glb/ + thumbs/ + meta.json) the webapp can import later in a separate change. Nothing in webapp changes now. |
| Independent copy | Standalone sandbox/showcase; no export contract; webapp keeps its own copy of the generator. |
| Webapp fetches at runtime | The game loads GLBs over HTTP from factory.railisland.com. |

**Answer: Source for later import.**

### Which package manager and command should build the GLBs?
| Option | What it means |
|---|---|
| pnpm, like webapp | `pnpm build` builds GLBs + site; same toolchain, lockfile and CI setup as webapp. |
| npm literally | `npm run build`; package-lock.json; CI uses `npm ci`. |

**Answer: pnpm, like webapp.** "npm build" in the request is read loosely.

### Are the generated GLBs and thumbnails committed to git?
| Option | What it means |
|---|---|
| Gitignored, built on demand | Only code is committed; the build is deterministic; CI rebuilds. Consumers run the build. |
| Committed | GLBs + thumbs checked in so a consumer can copy them without running the factory. |

**Answer: Gitignored, built on demand.**

### What should the factory export look like for the webapp's later import?
| Option | What it means |
|---|---|
| glb/ + thumbs/ + meta.json | Mirror vlakosimdb: one output folder with `glb/<id>.glb`, `thumbs/<id>.png` and a generated meta.json with id, title, group, defaultScale, license etc. - the catalog-entry fields move to the factory. |
| glb/ + thumbs/ only | Files only; catalog metadata stays hand-written in the webapp's `buildings.meta.json`. |

**Answer: glb/ + thumbs/ + meta.json.**

### How are model families organised in the factory?
| Option | What it means |
|---|---|
| Generic families | Skyscrapers are the first family of a registry; a later kind of model is a new family, not a new pipeline. |
| Skyscrapers only | Port the ten towers as-is; generalise when a second kind of model shows up. |

**Answer: Skyscrapers only.**

### Which parts of the webapp Creator should the factory site have?
| Option | What it means |
|---|---|
| Catalog + 3D preview | Table and card views, sort on every column, search, click-to-open interactive three.js preview with the thumbnail. No sign-in, uploads, woods or packages. |
| Add a GLB download | As above plus a download per model and a zip of the whole export. |
| Minimal gallery | Thumbnail grid + 3D viewer only. |

**Answer: Catalog + 3D preview.**

### How is the site hosted on Cloudflare?
| Option | What it means |
|---|---|
| Assets-only Worker | Like the webapp's embed site: a static SPA plus generated GLBs/thumbs/catalog JSON, no bindings, no server code. Public, no auth. |
| Worker with code | A Worker script in front, room for an API later. |

**Answer: Assets-only Worker.**

### Which branches deploy where?
| Option | What it means |
|---|---|
| master -> factory.railisland.com only | One environment; every push to master builds and deploys; manual dispatch for any branch. |
| master -> dev, stable -> prod | Mirror webapp with two Workers and a release step. |

**Answer: master -> factory.railisland.com only.**

### What gates the deploy?
| Option | What it means |
|---|---|
| Tests in a separate workflow | Deploy only builds; a test workflow runs typecheck + Vitest in parallel and shows red without blocking. |
| Tests block deploy | Deploy needs typecheck + tests green first. |

**Answer: Tests in a separate workflow.**

### How is the Vitest suite carried over?
| Option | What it means |
|---|---|
| Port model tests, drop catalog ties | Keep winding, triangle budget, y = 0 base, height > 2x width, determinism; check against the factory's own meta instead of the webapp's `buildings.meta.json`; add tests for the catalog JSON. |
| Port verbatim where possible | Minimal adaptation, fewer new tests. |

**Answer: Port model tests, drop catalog ties.**

### How does the factory get the webapp code it depends on (thumbnail rasterizer, GLB reader, Creator table/viewer components)?
| Option | What it means |
|---|---|
| Copy and trim | Copy what is needed and cut it down to what the factory uses (no uploads, no vehicle side view, no i18n). The factory evolves independently. |
| Shared package | Extract common code into a package both repos consume; requires changing the webapp. |

**Answer: Copy and trim.**

### What does the factory site's UI language and docs setup look like?
| Option | What it means |
|---|---|
| English only + CLAUDE.md + docs/ | Internal tool, no i18n machinery; CLAUDE.md, README quickstart and a docs/ folder following webapp conventions. |
| English + Czech | Small i18n layer with two catalogs. |

**Answer: English only + CLAUDE.md + docs/.**

## High-level plan

1. **Project skeleton.** A pnpm + TypeScript (strict) + Vite + Solid + Vitest
   project, Node 22, in the same shape as the webapp, with `CLAUDE.md`, a README
   quickstart and a `docs/` folder (index + one file per subsystem).
2. **Generator port.** The mesh builder and the ten skyscraper designs move over
   verbatim in behaviour (same ids, same palette, same deterministic bytes). The
   thumbnail rasterizer and the GLB triangle reader are copied and trimmed to the
   building path. The catalog-entry fields the webapp kept in `buildings.meta.json`
   for the `sky-*` entries (title, group `skyscraper_c`, defaultScale 0.5, category,
   license/author) move into the factory, attached to each design.
3. **Build = export.** `pnpm build` runs the generator first and writes the export
   folder: `glb/<id>.glb`, `thumbs/<id>.png` and a generated meta.json - the
   contract a later webapp import mirrors, like `vlakosimdb`'s export. The same step
   writes the site's catalog JSON (per model: id, title, group, triangles, file
   size, bounding box, thumbnail and GLB paths), then Vite builds the site with the
   export copied in. The generator alone stays runnable for fast iteration.
4. **Catalog site.** A Solid single-page app, English only: a table view and a
   card view, sort on every column, search, and a click-to-open detail with the
   thumbnail and an interactive three.js preview of the real GLB. Components are
   copied from the webapp Creator and trimmed of sign-in, origin switch, uploads,
   woods and packages.
5. **Tests.** The model tests are ported (outward winding, < 4,000 triangles,
   base at y = 0, height > 2x width, determinism / unchanged-is-byte-identical,
   removed designs are deleted) and checked against the factory's own metadata;
   new tests cover the meta.json and catalog JSON shape.
6. **Deploy.** An assets-only Cloudflare Worker named for the factory, serving the
   Vite output on the custom domain `factory.railisland.com`. A GitHub Actions
   workflow deploys on every push to `master` and on manual dispatch for any
   branch, building with pnpm and deploying with `wrangler deploy`, using the same
   `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` secrets as the webapp. A
   separate test workflow runs typecheck + Vitest in parallel without blocking.

Phases 2-3 come first; the site (4) consumes the catalog JSON from 3; deploy (6)
needs 3 and 4.

## Database and persistent storage

Nothing persistent is stored. No database, R2, KV or browser storage of user data.
The export folder and the site build output are gitignored, regenerated by every
build and deployed as static assets of the Worker; the Cloudflare deployment holds
only the latest build. The new on-disk contract is the export's meta.json (one
entry per model: id, title, group, category, defaultScale, glb and thumb file
names, license, author), written by the build and read by nobody yet - the
webapp's later import is the intended reader.

## Architecture decisions

- **Factory owns generation; webapp imports later.** Mirrors the vlakosimdb
  arrangement the webapp already understands, keeps generator code out of the
  game's build, and lets the meta.json shape be fixed before anybody consumes it.
  The alternative of the game fetching models from the factory at runtime was
  rejected (cross-origin, no versioning).
- **Gitignored output.** The generator is deterministic, so committing output adds
  diffs without adding information. The price is that a consumer must run the
  factory build.
- **Assets-only Worker, one environment.** No server code means nothing to secure
  and no bindings; a single `master` deployment fits an internal tool. A Worker
  script or a dev/stable split can be added later without moving the content.
- **Copy and trim, not a shared package.** Respects "change only the factory repo"
  and matches how the webapp itself diverged from its Roblox origin. Fixes made in
  one copy do not reach the other.
- **Skyscrapers only.** No family registry until a second kind of model exists.

## Weaknesses and risks

- **Two copies of the generator.** If the webapp branch `ccr-5f803b9b-ohwby3` is
  merged as is, the webapp and factory both carry the skyscraper code until the
  webapp import lands. Likely; cost is drift. Mitigation: merge that branch's
  catalog changes only once the webapp imports from the factory (a separate,
  webapp-side change).
- **Byte compatibility.** The ids and GLB bytes must stay identical to what the
  webapp branch produces, or the webapp's LOD cache and any saved maps that already
  hold `sky-*` ids diverge. Mitigation: port the determinism test and compare a
  build against the webapp branch's output once.
- **Copied viewer code drifts** from the webapp Creator; acceptable for a tool.
- **Custom domain provisioning** needs the API token to carry zone-scoped
  `Workers Routes: Edit` over `railisland.com`, as the webapp's dev deploy does;
  the repository secrets must be added to `rail-island-factory` by hand.
- **Deploy is not gated by tests**, so a broken design can reach the site. Cheap
  to fix forward; the test workflow shows it red.
- **Open:** where exactly the export folder lives and what it is called is left to
  implementation, as long as it is one folder with `glb/`, `thumbs/` and meta.json.

## Out of scope

- Any change to `rail-island-webapp`, including removing the generator from the
  `ccr-5f803b9b-ohwby3` branch or writing the webapp-side import.
- Sign-in, uploads, woods, packages, downloads and zips on the site.
- Other model families than skyscrapers; a family registry.
- Dev/stable split, release versioning, i18n.
